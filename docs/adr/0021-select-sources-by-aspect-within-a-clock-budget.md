## JEV 公式の事実（2026-09-23 に確認）

- 1回のリクエストには、1つの `state` と、名前を付けた複数の問いを載せられる。問いはどれも同じ `state` について、互いに独立に、
  並列に答えられる。問いを足しても応答時間はほとんど変わらず、増えるのは問いの分のトークンだけ。`state` が違えば別のリクエストになる。
  （https://api.typesafe.ai/openapi.json の `SystemOneRequest`・`questions`、https://docs.typesafe.ai/primitives.md 「Ask multiple
  questions together」、https://docs.typesafe.ai/patterns/fan-out.md。13問を1回にまとめると12.2倍安く10.0倍速く、答えは変わらない:
  https://docs.typesafe.ai/cookbooks/parallel_questions.md）
- 問いの `instructions` は構造（オブジェクト）でもよく、比べる相手（ここでは主張）を問いの側に入れれば、同じ `state` に対して相手ごとに
  1問ずつ、1回のリクエストで問える（https://docs.typesafe.ai/primitives/noul.md 「Structured instructions」）。
  境界が微妙な問いは `criteria` の `true`・`false` で「はい／いいえ」の意味を決める。線はコードで持つ（同ページ）。
- 上限（jev-1.13）: **1,200 リクエスト/分、250,000 トークン/秒**。どちらかを超えると `429 Too Many Requests`。1リクエスト 64k トークン
  （`state` と最長の問いで 32k）。料金は入力 100万トークンあたり $0.042（出力は無料）。上限は「予告なく変わりうる」。
  英語が主な学習言語で、精度が最も高い（https://docs.typesafe.ai/models.md）。
- `429` と `529 Overloaded` は、間隔を空けて（指数的に）送り直す（https://docs.typesafe.ai/api.md 「Handling rate limits」）。
  公式 SDK の既定: 送り直しは2回まで、間隔は 0.5秒から倍々で最大5秒、`retry-after`・`retry-after-ms` は60秒まで従う、
  対象は 408・429・500〜599（https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy.md）。1回の試行の既定の時間は10秒
  （https://docs.typesafe.ai/sdk/javascript/api/interfaces/TypeSafeClientConfig.md）。
- 関連の判定の手本（https://docs.typesafe.ai/cookbooks/classifying_rag_passages.md）: 資料1件につき1リクエストで、その1件について
  問う（1つのリクエストに複数の資料を並べない）。関連の線 `relevant_min` 0.45 は「出発点であって既定値ではない」。
  同時に投げるのは4本（公開の窓口には上限があるため）。問いの言葉とほぼ同じでも別の側面（アクセストークンの寿命を問うのに、署名鍵の寿命の
  資料）は関連 0.08 以下と答えている。矛盾する資料は捨てずに別枠に置く。
- 判定に無関係な内容で `state` が大きくなるほど精度が落ちる。文字どおりに読むので、条件は `criteria` に書く
  （https://docs.typesafe.ai/model-jaggedness/jev-1.13.md）。

## 手順（何を・どの順に・どう処理するか）

実装は `src/lib/pipeline/source-selection.ts`（全体の流れ）、`candidate-order.ts`（順）、`relevance-question.ts`（関連の問い）、
`jev-dispatcher.ts`（JEV への送り方）、`time-budget.ts`（時間と上限の設定、1か所）。

1. **候補は池の全ページ。** その主張のファクトチェックの結果（Google Fact Check で見つかり、JEV が同じ主張と照合したもの）も、
   その主張だけの候補にする。JEV が判定する前に落とす上限は無い（ADR-0016 の手順2を廃止）。
2. **節に分ける。** ADR-0014 の分け方のまま（削らない）。
3. **主張ごとの順を決める**（`orderForClaim`）。
   1. その主張のファクトチェックの結果。
   2. 一次資料（ADR-0016 のアドレスで見分ける印: go.jp・lg.jp・e-Gov・ac.jp・DOI 等）のページを、ほかのどのページよりも先に。
   3. 一次資料の中でも、それ以外の中でも: この主張の検索で見つかったページ → 記事全体の検索 → ほかの検索。各検索は書かれた順、
      ページはその検索の順位（複数の検索に出たページは最も前の位置）。同順は URL の文字コード順。
   4. 同じ出所（ADR-0016: 同じサイト、本文がほぼ同じ転載）のページは、その出所の最初の1件の位置にまとめる。転載は元と一緒に判定される。
   ページの順の中では節は読む順。こちらの点数（語の出現回数・文面の重なり）は使わない。
4. **主張を交互に回す**（`interleave`）。各主張の最初の候補（節）を主張の順に1件ずつ取り、次に各主張の2件目、…と進む。
   すでに取った節は飛ばす。どの主張も、ほかの主張の深い候補より先に、自分の最初の候補を判定される。
5. **関連を JEV に問う。** 1節1リクエスト。`state` はその節だけ（`{ section: { title, url, text } }`）。問いはその節が候補になっている
   主張ごとに1問（池のページは全主張、ファクトチェックの結果はその主張だけ）で、全主張の分を同じリクエストにまとめる
   （入力上限を超えるときだけ、同じ節のまま主張を分けて複数のリクエストにする）。問いの文面は下の「関連の問い」。
6. **振り分けはコードの線だけ**: JEV の答えが `RELEVANCE_THRESHOLD`（0.45、`src/lib/jev/bands.ts`、ADR-0014 のまま）以上なら関連あり。
7. **時計で止める**（`time-budget.ts`、下の「時間の予算」）。開始から225秒を過ぎたら、新しい関連の判定を始めない。判定中のものは
   終わるか、試行の時間（15秒）が切れるまで待つ（遅くとも240秒）。始められなかった候補・途中で切れた候補・JEV が答えなかった候補は、
   主張ごとに理由と一緒に記録する（手順9）。関連の判定がすべて終わったら（早ければ225秒より前に）、すぐ信頼度の問いに進む。
8. **信頼度の問い**（ADR-0011 の文面のまま）。主張ごとに、関連ありの節を、手順3〜4で判定した順（その主張の順）に取り、
   **1主張4リクエスト分**（`SUPPORT_REQUESTS_PER_CLAIM`、見積もり 約12万トークン）に収まるまで入れる。入り切らない節は
   `evidenceTrace.heldBack` に理由と一緒に残す。入れた節は ADR-0016 の決まった順（一次資料を含む出所→出所名→出所の中の一次資料→URL）で、
   出所ごとにまとめて `sources` に入れる。複数のリクエストに分かれたときは答えの最大を取る（ADR-0014 のまま）。関連する節が0件なら
   `sources` を空にして同じ問いを立てる。どれか1つでも答えが返らなければ、その主張は数値を出さずに失敗として残す（今までどおり）。
   主張ごとの1つ目のリクエストを先に、主張を交互に回して送る。
9. **記録。**
   - `evidenceTrace`: `found`（池のページ数）、`sections`（候補の節の数）、`judged`（JEV が答えた節）、`relevant`（線以上）、
     `unjudged`（判定されなかった節を理由ごとに: 理由・節の数・ページの URL を判定する予定だった順に）、`heldBack`（信頼度の問いに
     入り切らなかった節）、`used`・`saidNothing`・`origins`。`overCap` は常に0（判定の前に落とすものは無い）。
   - ログ: 主張ごとに判定されなかった節の数と理由を1行。実行ごとに、関連の判定の送信数・始められなかった数・打ち切り・失敗・再試行を1行と、
     判定されなかったページの URL を理由ごとに20件ずつの行で。
   - `result.timings`: 段ごと（`extraction`・`queryGeneration`・`search`・`pageFetch`・`factCheck`・`relevanceJudging`・
     `supportJudging`）の時間（ms、仕事が走っていた時間。段は重なりうるので開始・終了の時刻も）と、JEV の段には呼び出し回数
     （`jevCalls`・`jevRetries`・`jevFailures`・`jevCutOff`・`jevNotStarted`）。観測のためだけで、何も決めない。

### 関連の問い（1問1判断。state は節だけ）

```json
{
  "type": "noul",
  "instructions": {
    "claim": "<記事の原文の文（claim.original）>",
    "aspect": "「<②の about>」の「<②の kind の語>」",
    "question": "Does `section` state anything about `aspect`, the point that `claim` makes?"
  },
  "criteria": {
    "true": "`section` states something about `aspect` for the same target as `claim`, whether it agrees with `claim` or contradicts it.",
    "false": "`section` states nothing about `aspect`: it covers only other points of the same broad subject, or a different target with a similar name."
  }
}
```

- 訳: 問い「`section` は、`claim` が述べている点である `aspect` について何かを述べているか」。はい＝`claim` と同じ対象の `aspect` について
  何かを述べている（`claim` と一致していても食い違っていてもよい）。いいえ＝`aspect` について何も述べていない（同じ大きな題材の別の点だけ、
  または名前の似た別の対象）。
- `aspect` は②（ADR-0019）が主張ごとに書いた `about`（何について）と `kind`（事実の種類）から作る。`kind` は②の指示文の語で書く
  （time→「時期・開始年・施行日・期間」など）。例: 「ワンストップ特例 申請書」の「時期・開始年・施行日・期間」。②が書けなかったときは、
  抽出の `subject` を `about` の代わりにする。どちらも無ければ `aspect` を付けず、問いは「`claim` が述べている点について」になる。
- 主張の文は記事の原文のまま（ADR-0011・0014）。言い換え（normalizedText）は渡さない。記事全体も渡さない（ADR-0014）。
- 文面は英語、データ（主張・側面・節）は書かれたままの日本語。英語が JEV の最も精度の高い言語であり（models「Language support」）、
  問いは1リクエストに主張の数だけ載るので、短いほど入力が減る（29主張で問いは約8,000見積もりトークン、節は数百〜約5,000）。

### ページで先に絞るか: 絞らない（理由）

- #84 の段1（題名・URL・抜粋で「同じ対象か」、線0.2）は、50ページのうち0ページしか落とさなかった。
- 節の問いは全主張の分を1リクエストにまとめる。ページで絞って節のリクエストを減らせるのは、どの主張の側面にも触れないページだけで、
  一つの題材の記事ではそういうページは少ない。絞ってもリクエスト数（時間を決めるもの）はほとんど減らない。
- 抜粋だけで判定すると、ページの奥の節で側面を述べているページを取りこぼし、二度と見られない。ページの問いの分（約200回、約10秒）も使う。
- 代わりに、手順3〜4の順（一次資料・この主張の検索・順位が先）と時計で、各主張の見込みの高い候補から判定する。

### 時間の予算（`src/lib/pipeline/time-budget.ts` の1か所。時刻は実行の開始から）

| 設定 | 値 | 理由 |
| --- | --- | --- |
| 上限（`PLATFORM_LIMIT_MS`） | 300秒 | Vercel の `maxDuration`（vercel.json、analyze の route） |
| 締め切り（`RUN_DEADLINE_MS`） | 270秒 | JEV への依頼はすべてここまでに終える。残り30秒は、時計が動き出す前の起動・リクエストの読み取り、結果の組み立てと送信、混んだイベントループの分。打ち切られると何も返らないので、早めに返る側に倒す |
| 信頼度の問いの確保（`SUPPORT_RESERVE_MS`） | 30秒 | 29主張×最大4回＝116回、約350万見積もりトークン。250,000トークン/秒で約14秒、同時20本・1回約2秒でも約12秒。倍の余裕と1回の再試行分 |
| 1回の試行（`JEV_ATTEMPT_TIMEOUT_MS`） | 15秒 | 変更前のクライアントの値。段の締め切りまでの残りより長くは与えない |
| 最小の試行（`MIN_ATTEMPT_MS`） | 5秒 | 残りがこれ未満なら、始めない・送り直さない |
| 関連の判定を新しく始めない（`RELEVANCE_STOP_MS`） | 225秒 | 270 − 30 − 15。判定中のものが試行1回分で終わっても、信頼度の問いの30秒が残る |
| 関連の判定が終わる（`RELEVANCE_END_MS`） | 240秒 | 270 − 30。信頼度の問いはここまでに始まる（関連が早く終われば、その時点で始まる） |
| 信頼度の問いの上限（`SUPPORT_REQUESTS_PER_CLAIM`） | 1主張4回 | 手順8。確保した30秒に収めるため。記事05と同じ大きさの池で試すと（7節に1節が全主張に関連ありとした厳しめの試し）、上限が無いと約950回が要り、全主張が数値なしになった。上限があれば29主張で最大116回（約350万見積もりトークン、250,000トークン/秒で約14秒）。4回＝約12万見積もりトークンは、#80 で1主張に渡していた量と同じ。答えの最大を取る回数（ADR-0014）も増えすぎない |

締め切りは見積もりではなく、実行中に時計で守る。①主張の取り出し・②検索語の作成（生成 LLM）にはこの予算の上限を入れていない（①②は変えない）。
①②が遅いと③に使える時間が減り、時間切れの候補が増える（段ごとの時間で見える）。

| 設定 | 値 | 公式の根拠 |
| --- | --- | --- |
| 1分あたりの回数（`JEV_REQUESTS_PER_MINUTE`） | 1,200回。1分に固めず1秒20回にならす | models。1分の数え方は公開されていないので、一度に使い切らない |

| 失敗の数え方 | 最後まで答えが無いものだけを「各サービスの状態」の失敗に数える。送り直して答えが来たものは再試行の回数だけ。段の締め切りで打ち切ったものは時間切れで、JEV の失敗に数えない | ADR-0006 の層を分けるため |

## ガイドライン（こうする）

- 関連は「主張の側面について何かを述べているか」を問う。同じ大きな題材を扱っているだけ、名前が似ているだけでは「いいえ」。
- 主張と食い違う節は「はい」。矛盾を捨てない（ADR-0016）。
- 同じ `state`（節）に対する問いは、全主張の分を1回のリクエストにまとめる（ADR-0007: まとめられる問いを分けない）。
- 候補の順は、アドレス（一次資料か）・検索（誰の・何本目の・何位）・出所だけで決める。同じ池なら何度流しても同じ順。
- 時間は時計で守る。設定は `time-budget.ts` の1か所で変える。線は `bands.ts` の1か所。
- 判定しなかったもの・入り切らなかったものは、主張ごとに理由と一緒に記録とログに残す。
- 段ごとの時間と JEV の呼び出し回数を `result.timings` に出し、本番の測定で①②③のどこに時間がかかっているかを見る。

## 禁止事項（これはしない）

- 関連をこちらの文字列処理で決める（主張の語・主語・略語・固有名詞の文字列の一致で、節を通す／落とす）。
- JEV が判定する前に、こちらの判断（検索の順・点数・上限）で候補を捨てる。
- 見積もり（「〜秒で終わるはず」）で時間を決め、時計を見ない。
- 締め切りを過ぎてから新しい判定を始める。締め切りまでに答えが届かない送り直しをする。
- 判定しなかった候補・入り切らなかった節を黙って捨てる。
- 答えが返らなかった信頼度の問いに数値を作る。一部の答えだけで数値を出す。
- 実行ごとに変わる順（並列処理の完了順、Map/Set の挿入順、言語設定に依存する比較）で問う・渡す。
- 1つの問いに2つの判断を詰める。食い違う節を関連なしとして扱う。
- 公式の上限（1,200回/分・250,000トークン/秒）を超えて送る。混んでいると言われた JEV に重ねて送る。
- 信頼度の問いの文面、表示、80%の線（ADR-0011）を変える。①（ADR-0020）と②（ADR-0019）を変える。

## 向かう方向（ADR-0013 の③）

- 理想: 一次資料（データ表・法令文書・所管官庁・提唱元）を優先し、主要な点は独立した複数の出所で確かめる。1件ごとに関連・使えるか・
  矛盾を判定し、矛盾は捨てずに別枠に残す（IFCN、JEV cookbook classifying_rag_passages）。
- 逆向き: 検索結果の上位だけを見る。JEV に聞く前にこちらの判断で候補を捨てる。こちらの文字列処理で関連を決める。
  同じ出所の転載を別々の裏付けと数える。矛盾を黙って捨てる。
- この決定で向き直すもの:
  - 候補は JEV の判定の前に1件も落ちない（`overCap` 0）。時間で判定できなかった分は捨てたのではなく、理由付きで数えて残す。
  - 関連を「同じ題材か」ではなく「主張の側面について述べているか」で JEV が決める。題材が同じだけの節は信頼度の問いに入らない。
  - 一次資料を先に判定する。同じ出所はまとめて判定し、信頼度の問いでも1つの出所として渡す（ADR-0016 のまま）。
  - 同じ入力なら同じ順で判定する。判定の深さだけが時間で変わる。
- まだ残るもの: 「使えるか（`contains_answer_evidence`）」「矛盾か（`contradicts_query_premise`）」を別の問いで判定し、矛盾を別枠に置く
  段階は無い。いまは関連ありの節を矛盾も含めて同じ `sources` に入れている。

## ADR-0016・ADR-0014 から置き換える部分

- ADR-0016 の**手順2（関連判定の前の上限、1主張 見積もり12万トークンを検索の順に埋める）**を廃止する。上限は、JEV が関連ありと
  判定した節を信頼度の問いに入れるところ（手順8、1主張4回分）にだけ置き、入り切らない分を記録する。
- ADR-0016 の**手順1の並び**（この主張の問い→記事全体→ほか）を、手順3の並び（一次資料が先、同じ出所をまとめる）に置き換える。
  この並びは判定の順と、信頼度の問いに入れる順にだけ使う。信頼度の問いの中の並び（ADR-0016 の手順5）は変えない。
- ADR-0014 の**「1回目: 関連を JEV に問う」**（主張ごとに、その主張の全節を1つの state に並べて「同じ事柄について述べているか」を問う）を、
  手順5（1節1リクエスト、節だけの state、全主張の側面の問い）に置き換える。
- 残すもの: ADR-0014 の節の分け方、関連の線 0.45、関連ありの節だけを信頼度の問いに渡すこと、記事全体を渡さないこと、複数のリクエストでは
  答えの最大を取ること。ADR-0016 の手順3〜5・7〜8（出所・一次資料・決まった順・出所ごとに渡す）と禁止事項。ADR-0011 の文面・表示・80%の線。

## Consequences

- 北極星③の逆向き（上位だけを見る、判定の前に捨てる、題材が同じなら通す）を向き直す。狙い: 関連判定の前に落ちる候補が0になり、
  各主張で一次資料と自分の検索の上位から JEV が判定する。題材が同じだけの節が信頼度の問いから外れる。渡る資料の量が回ごとに大きく
  変わること（文18の後半の10件↔17件、43↔62%）が減る。
- 必ず270秒以内に返る（①②が遅い場合を除く）。
- 恐れ:
  - 池の節（約1,200〜3,300）に対して20回/秒では、多くの場合225秒までに判定しきれず、時間切れの候補が残る。判定の深さは JEV の速さと
    ①②の終わる時刻で回ごとに変わり、値が揺れうる（順は固定なので、揺れるのは最後の方の候補だけ）。節の大きさ（ADR-0014、平均約640字）を
    変えるかは、測ってから別の変更で決める。
  - 実行時間が延びる（約232〜244秒。前回184〜195秒）。JEV の費用が約 $0.3〜0.7/記事に増える（全主張の問いを節ごとに送るため）。
  - 問いの文面を英語にし、1節ずつ問うようにしたので、関連の答えの傾向が前と変わる。線 0.45 は測りながら動かす。
  - 関連ありの節が4回分を超える主張では、判定の順の後ろの節が信頼度の問いに入らない（`heldBack` に残る）。
  - 1つの節のリクエストが答えを得られないと、その節は全主張で「判定の失敗」として残る（主張ごと失敗にはしない。信頼度の問いは
    判定できた節で行う）。
  - 主張が非常に多い記事（60件超など）では、1主張4回でも信頼度の問いが30秒に収まらないことがある。そのときは後ろの主張が
    「確認できませんでした」になる（数値は作らない）。
- 気づいたこと（この変更では直さない。層3/2）: 見積もりのために実物のページを読んだところ、取得（`HTTPFetchProvider`）は文字コードを見ずに
  UTF-8 で読んでいた。Shift_JIS の総務省のページ（ふるさと納税の一次資料）は文字化けしたまま池に入る。
- 効果は未測定。ADR-0012 の物差しで記事05を2回流し、前回（184秒・195秒）と比べる: 予測「高」の文15・文18後半が80%を超えるか、
  回ごとの揺れ（最大19点）、仕込んだ4か所が低いままか、`result.timings` の段ごとの時間、`unjudged`・`heldBack` の件数。
- 戻し方: マージ後 `git revert -m 1 <マージのコミット>`。
