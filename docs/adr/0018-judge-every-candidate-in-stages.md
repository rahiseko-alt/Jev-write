# 資料は池の全候補を JEV が段階で判定する（ページ→節→信頼度）。こちらは線で振り分けるだけ（北極星③の残る逆向きを直す）

## 向かう方向（ADR-0013 の③、ADR-0007）

- 理想: 1件ごとに関連を判定する（IFCN、JEV cookbook classifying_rag_passages）。判定は JEV が行い、こちらのコードは渡すものを揃えて、
  返ってきた数値を線で振り分けるだけ（ADR-0007）。
- 逆向き: 検索結果の上位だけを見る。JEV に聞く前にこちらの判断で候補を捨てる。こちらの文字列処理で関連を決める。
- この製品の目的は正誤を決めることではなく、信頼度のブレを管理すること（ADR-0012）。資料の選び方も
  「何を・どの順に・どう処理するか」「やってはいけないこと」を固定する。同じ入力なら、同じ資料が同じ順で JEV に渡る。

## Context

ADR-0016 のあとの本番（記事01を2回、change-log の「測定」行）で、③に逆向きが2つ残っていた。

1. **関連判定の前に、先頭だけを残して落としていた。** 資料の池の候補は1主張あたり平均186件、そのうち平均168件は
   JEV の関連判定にかかる前に落ちていた（`evidenceTrace.overCap`）。ADR-0016 の手順2の上限（1主張 見積もり12万トークン）を、
   検索の順（その主張の問い→記事全体の検索語→ほかの主張の問い）の先頭から埋め、収まらない分を捨てていたためである。
   並びは関連と無関係で、実質「検索結果の上位だけを見る」「こちらの判断で候補を捨てる」（ADR-0007）になっていた。
2. **関連の線を、主張と対象の違う節が通っていた。** 関連の問いは「sources[i] のこの節は、claim.original と同じ事柄について述べているか」
   （ADR-0014）で、1つの state に主張の全節を並べて問うていた。SIPS（消費行動モデル）の主張に、AISAS だけを説明するページや、
   略語の似た金融用語 SIP（Share Incentive Plan など）のページの節が 0.45 を越えて入り、信頼度の問いの材料を濁らせた
   （E2: SIPS の Identify を Interest と書いた文が、Identify と書く提唱者のページがあるのに信頼度92〜96%）。

JEV 公式（2026-09-23 に確認。`https://api.typesafe.ai/openapi.json`、`https://docs.typesafe.ai`）:

- primitives/noul: Noul は1問1判断。境界が微妙なときは `criteria` の `true`・`false` で「はい／いいえ」の意味を決める。
  線はコードで持つ。例示の振り分けは YES 0.8・NO 0.2（間は人へ）で、「本当の『はい』を取りこぼすと高くつくときは線を下げる」。
  `instructions` は構造（オブジェクト）でもよく、比べる相手（ここでは主張）を問いの側に入れて、同じ state に何件でも問える
  （Structured instructions の例: 履歴書を state に、候補の記録を1問ずつ）。
- cookbooks/classifying_rag_passages: 資料1件につき1リクエストで、state は「問い＋その1件」。関連の線 `relevant_min` 0.45
  （「出発点であって既定値ではない」）。同時に投げるのは4本（公開の窓口には上限があるため）。
- patterns/fan-out: 同じ state に対する問いは1回にまとめ、どれを使うかはコードが決める。
  primitives「When one question depends on another」・cookbooks/skill_suggestion: 次の問いの state が前の答えで決まるときだけ
  2回目を送る（全候補を安く読み、残ったものを詳しく読む）。
- model-jaggedness（jev-1.13）: 判定に無関係な内容で state が大きくなるほど精度が落ちる。先に絞り、問いに要るものだけを送る。
  絞れないときは Noul で関連を判定して絞る。
- models: 入力100万トークンあたり $0.042（出力は無料）。上限は 250,000 トークン/秒・1,200 リクエスト/分、
  1リクエスト 64k（状態＋最長の問いで 32k）。api: 429 と 529 は間隔を空けて再試行する。SDK の既定は 408・429・500〜599 を再試行。

## Decision

### ADR-0016・ADR-0014 のうち、この決定で置き換える部分

- ADR-0016 の**手順2（関連判定の前の上限）**を廃止する。候補は関連判定の前には1件も落とさない。上限は下の手順4に置き換え、
  JEV が段1で「主張の対象について述べている」と判定したページにだけ当てる。
- ADR-0016 の**手順6**と ADR-0014 の**「1回目: 関連を JEV に問う」**（1つの state に主張の全節を並べ、
  「同じ事柄について述べているか」を節ごとに問う）を、下の手順2・5（段1・段2）に置き換える。
- 残すもの: ADR-0016 の手順1（候補は池の全ページ、主張ごとの順）、3〜5（出所でまとめる・一次資料かを付ける・決まった順）、
  7〜8（線以上の節だけを出所ごとに信頼度の問いへ）と禁止事項。ADR-0014 の節の分け方と、記事全体を渡さないこと。
  ADR-0011 の信頼度の問いの文面、表示、80%の線（ADR-0011・`FLAG_THRESHOLD`）は変えない。

### 手順（この順番で行う）

1. **候補は池の全ページ。**（ADR-0016 の手順1のまま）主張ごとの並びは、その主張の問いの検索→記事全体の検索語→ほかの主張の問いの
   検索、各検索の中では検索が返した順位のまま。この並びは手順4の上限にだけ使い、関連には使わない。
2. **段1（ページ）: 池の全ページを、1ページ1回、全主張について JEV に問う。** state はそのページの題名・URL・検索結果の抜粋だけ
   （`{ page: { title, url, excerpts } }`。抜粋は検索した順に重複なく。抜粋が無いページは本文の最初の節を抜粋の代わりにする）。
   問いは主張ごとに1つの Noul（下の「問いの文面」）。主張は問いの `instructions` に入れる（公式の Structured instructions）。
   リクエストはページの URL の順（文字コード順）に送る。64k・32k の上限を超えるときだけ、問いを複数のリクエストに分ける。
3. **振り分け（コード）: 段1の答えが線（0.2）以上なら次へ、未満なら落とす**（JEV が「別の対象」と判定したもの。`offSubject` に数える）。
   段1の答えが返らなかったページ（再試行のあとも失敗、または大きすぎて問えない）は、落とさずに次へ送る（`unscreened` に数える）。
4. **上限（コード）: 1主張あたり、段2に送るページは見積もり 240,000 トークンまで**（`SECTION_STAGE_TOKEN_BUDGET`）。
   その主張の事実確認の照会で見つかった結果（JEV が照会時に主張と照合済み。段1は通さない）を先に、続けて手順3を通ったページを
   手順1の並び（その主張の問いの検索→記事全体の検索語→ほかの主張の問い、各検索の順位）で入れ、収まらないページは飛ばして次を入れる。
   入らなかったページの数を `overCap`、理由を `overCapReason` に入れ、URL をログに出す。
5. **段2（節）: 手順4で入ったページを節に分け（ADR-0014 の分け方、削らない）、1節1回、そのページを通した主張だけに JEV に問う。**
   state はその節だけ（`{ section: { title, url, text } }`）。問いは主張ごとに1つの Noul（下の「問いの文面」）。
   リクエストはページの URL の順・節の順に送る。
6. **振り分け（コード）: 段2の答えが線（0.45）以上の節だけを残す。** 主張と食い違う節も「同じ対象について述べている」ので残る。
   段2の問いが再試行のあとも答えられなかった主張は、材料を判定できていないので、数値を出さずに失敗として残す（ADR-0003・0006）。
7. **信頼度の問い（ADR-0016 の手順3〜5・7〜8のまま）:** 段2にかけたページに出所と一次資料かを付けて決まった順（一次資料を含む出所→
   出所名→出所の中の一次資料→URL）に並べ、手順6で残った節をその順のまま出所ごとにまとめて、ADR-0011 と同じ文面の Noul を問う。
8. **記録:** `evidenceTrace` に、候補数 `found`・段1で別の対象 `offSubject`・段1で判定できず送った `unscreened`・上限 `overCap`
   （と `overCapReason`）・段2で関連する節が無かった `saidNothing`・根拠 `used`・独立した出所 `origins` を出す。主張ごとに1行ログに出す。

### 問いの文面（1問1判断: 同じ対象か）

段1の Noul（主張1件につき1問。state は `page`）:

```json
{
  "type": "noul",
  "instructions": { "claim": "<記事の原文の文（claim.original）>", "question": "`page` は、`claim` が述べている対象について述べているか。" },
  "criteria": {
    "true": "`claim` が述べている対象そのもの（同じ名前で、同じ分野のもの）について述べている。述べている内容が `claim` と同じか違うかは問わない。",
    "false": "名前や略語が似ているだけの別の対象について述べている。または、別の対象だけを説明していて、`claim` が述べている対象には触れていない。"
  }
}
```

段2の Noul は、`question` が「`section` は、`claim` が述べている対象について述べているか。」で、`criteria` は段1と同じ。

- 「同じ対象か」の1つだけを問う。境界（略語の似た別物、別の対象だけの説明）は `criteria` で決める。
- 食い違いは `true` 側と明記する（「同じか違うかは問わない」）。矛盾を黙って捨てないため（ADR-0016）。
- 主張の文は記事の原文のまま（ADR-0011・0014）。言い換え（normalizedText）は渡さない。

### 線の値と理由（`src/lib/jev/bands.ts` の1か所）

| 段 | 設定値 | 値 | 理由 |
| --- | --- | --- | --- |
| 段1（ページ） | `PAGE_RELEVANCE_THRESHOLD`（`JEV_PAGE_RELEVANCE_THRESHOLD`） | 0.2 | 公式 cookbook の 0.45 を出発点に、取りこぼしを避ける側へ下げた。段1は題名・URL・抜粋しか見ないので判断材料が薄く、ここで落としたページは二度と見られない。通しすぎても段2で数問増えるだけ。公式 Noul のページの振り分け例で「はっきりした いいえ」とされる NO 0.2 を線にし、はっきり「いいえ」のページだけを落とす |
| 段2（節） | `RELEVANCE_THRESHOLD`（`JEV_RELEVANCE_THRESHOLD`） | 0.45 | 公式 cookbook（classifying_rag_passages）の `relevant_min`。ADR-0014 のまま |
| 信頼度 | `FLAG_THRESHOLD` | 0.8 | 変えない（ADR-0011） |

どちらの線も測りながら動かす（コードを変えずに環境変数で動かせる）。

### 上限の値と理由

- 値: 1主張あたり、段2に送るページは見積もり 240,000 トークン（`SECTION_STAGE_REQUESTS_PER_CLAIM` 8 × 状態の予算 30,000。
  日本語で約16万字、8,000字のページで約20件）。
- 置く場所: 段1のあと。段1にはすべての候補をかける（上限で段1を飛ばす候補は無い）。
- 理由: 300秒の上限を最悪でも超えないため。上限が無いと、どのページも触れる対象（例: 口コミ）についての主張は池のほぼ全ページを段2に
  送り、信頼度の問いも数十回に分かれる。上限があれば、段2は1主張 見積もり24万トークンまで、信頼度の問いは1主張9回以内に収まる
  （下の見積もり）。
- 順: その主張の問いの検索で見つかったページ→記事全体の検索語で見つかったページ→ほかの主張の問いのページ、各検索の順位。
  長い1ページが後ろの短いページまで締め出さない（収まらないページは飛ばして数える）。

### JEV の呼び出し方（`src/lib/providers/jev/client.ts`）

- **再試行:** Anthropic と同じ形（`src/lib/providers/retry.ts`）。429 と 5xx（529 を含む）は、retry-after があればその秒数、
  無ければ 2・4・8秒待って、同じリクエストを最大3回送り直す。それ以外（401・422 など）は送り直さない。
  最後まで混んでいたら失敗として数え、画面の「各サービスの状態」に出る（再試行の回数も）。時間切れ（1回15秒）と通信の失敗は送り直さない
  （Anthropic と同じ）。
- **同時に投げる数の上限:** 1回の実行で同時に8本まで（`JEV_MAX_CONCURRENT_REQUESTS`）。残りは出した順に待つ。
  公式 cookbook の同時数（classifying_rag_passages 4本、rerank_typesafe 12本）の間。429 で待つ間もその枠を持ったままにして、
  混んでいる JEV に重ねて投げない。

### 禁止事項（これはしない）

- 主語の出現回数・文面の重なりなど、こちらの点数で候補を並べて切る（#22・#39）。
- 検索結果の上位だけを見る（JEV の関連判定の前に、先頭から切る）。上限は段1のあと、JEV が対象と判定したページにだけ当てる。
- こちらの文字列処理で関連を決める（主語・略語・固有名詞の文字列の一致で通す／落とす）。関連は JEV が criteria に沿って決める。
- 同じ出所の転載を、別の裏付けとして重ねる（ADR-0016 のまま）。
- 落とした候補を黙って捨てる。段1で落とした数、上限で落とした数と理由、段1で判定できずに送った数を必ず記録に出す。
- 実行ごとに変わる順（並列処理の完了順、Map/Set の挿入順、言語設定に依存する比較）で JEV に渡す。
- 1つの問いに2つの判断を詰める（「同じ対象で、かつ裏付けているか」など）。信頼度の問いの文面・表示・80%の線を変える。
- JEV が答えなかった節を、関連ありとも関連なしとも決めつけて信頼度の問いに進む（その主張は失敗として残す）。

## 見積もり（記事01: 主張17〜19件、池 約190ページ）

実装の計画関数（`planPageRequests`・`planSectionRequests`・`planSupportRequests`）に、記事01の文18件と、次の仮定のページを
入れて数えた（2026-09-23、未測定）。見積もりトークンは日本語1字1.5トークンで多めに出る。実際の入力は見積もりの約2/3とみる
（ADR-0016 の実績: 見積もり12万に対し実際 約8万）。単価は $0.042/100万入力トークン（公式 models、出力は無料）。

仮定: 抜粋 約400字×1.3件/ページ、本文 約8,000字（約3節）/ページ、段1を通るページは50〜80%、1ページを通す主張は3〜6件、
段2で関連ありの節は3割。

| --- | --- | --- |
| 段1（ページ） | 190回（1回に18問） | 約130万 |
| 段2（節） | 約290〜460回 | 約150万〜280万 |

## Consequences

- 北極星③の残る逆向き2つが理想の向きに変わる: 候補は JEV の判定の前に1件も落ちない（上限は段1のあと、JEV が対象と判定した
  ページにだけ）。関連は「同じ対象か」を criteria で境界づけた1判断で JEV が決め、こちらは文字列で決めない。
- state が1ページ・1節だけになり、ほかに何が見つかったかで関連の答えが変わらない（ADR-0014 の Consequences で
  「関連の判定が揺れる場合、最初に疑う」とした、全節を1つの state に並べる形をやめた）。
- JEV の呼び出しが 約70〜90回/記事（ADR-0016 の見込み）から 約520〜760回/記事 に増え、費用は2〜4倍、実行時間は15〜30秒延びる見込み。
- 段2を「同じ対象か」にしたため、同じ対象の別の側面を述べる節も信頼度の問いに入る。材料が増え、信頼度の問いが複数回に分かれる
  （答えの最大を取る。ADR-0014）ことが増える。信頼度が上に寄る恐れがある。未測定。
- 段2の1回の失敗は、その節を通した主張すべてを失敗にする（旧来は1主張だけ）。再試行で起きにくくしたが、起きたら
  「確認できませんでした」になる。
- 主張が非常に多い記事（40件超）では、段1が「ページ数×主張数」で増え、300秒を超えるおそれがある。検証用の10本
  （1,600〜1,900字）は範囲内の見込み。超えたら、段1にも同じ順の上限を足すかを測ってから決める。
- 効果は未測定。ADR-0012 の物差し（仕込んだ文が低く出るか、同じ記事を複数回流したときの揺れ幅）で、記事01の前後を比べる。
  特に E2（SIPS の Identify）の信頼度、`overCap` が 0 近くになるか、実行時間と JEV の呼び出し回数を見る。
- 戻し方: マージ後 `git revert -m 1 <マージのコミット>`。
