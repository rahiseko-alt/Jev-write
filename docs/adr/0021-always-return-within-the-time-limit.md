# 解析は必ず300秒の手前で返す。締め切りは要求の開始から時計で数え、段ごとに打ち切り、間に合わなかった分は「時間切れ」として残す

## 向かう方向

- 理想: 貼った記事には、必ず結果が返る（何も返らない、を無くす）。そのうえで、どの段も締め切りにかからず、「時間切れ」が出ない。
  北極星（ADR-0013）の「同じ入力で値がほぼ揺れない」とも同じ向きである。時間切れは、その回の各サービスの速さで出たり出なかったりするので、
  揺れのもとになる。締め切りは安全網であって、ふだん通る道ではない。
- 逆向き: 300秒を超えて何も返らない（#84）。見積もりで時間を決めて時計を見ない（ADR-0018 は JEV の部分を22〜35秒と見積もったが、
  3文で92秒かかった）。時間切れで数値を作る、主張を黙って落とす、時間切れをサービスの失敗として数える（層が混ざる。ADR-0006）。
- 向かい方: 段ごとの時間（`result.timings`）を本番で測り、締め切りに近い段を速くする。締め切りの数値は測って直す（1か所）。
  文の取り出し（①）が締め切りに間に合わない長い記事は、①を分けて処理する別の変更でしか扱えない（この変更では主張0件で返す）。

## 経緯

- 本番（Vercel）は1回の実行が300秒を超えると打ち切り、利用者には何も返らない（ADR-0006 の層0、`FUNCTION_INVOCATION_TIMEOUT`）。
  #84 の記事05で起きた（change-log）。
- #84 を戻した本番（18923eb）で、記事05（1,552字・29主張）は184秒・195秒で終わった。`result.timings` には FactVerification の合計しか無く、
  どの段に何秒かかったかは分からない。
- ページの取得は、1回の実行ごとに3〜8件が10秒で切れている（"This operation was aborted"）。
- Anthropic の呼び出しには時間の上限が無く、429/529 の再試行（2・4・8秒、retry-after は最大60秒）にも全体の上限が無かった。JEV は1回15秒、
  Tavily・ページ・Google は1回10秒で切れるが、実行全体の締め切りはどこも見ていなかった。
- 検証用の記事は1,400〜1,770字。これより長い記事は測っていない。
- JEV 公式（2026-09-23 に確認）: API には時間の引数が無い（`SystemOneRequest` は `state`・`model`・`questions` だけ）。時間は呼ぶ側が持つ。
  公式 SDK の1回の試行の既定は10秒で、「再試行を含めた全体の上限は持たない」（`TypeSafeClientConfig.timeout`）。上限は 250,000 トークン/秒・
  1,200 リクエスト/分（models）。429・529 は間隔を空けて送り直す（api）。
- 時計と段ごとの時間の部品は、途中で止めた作業（956c377、未検証）から取り、作り直した。そこにあった関連の問い・候補の順の変更は入れていない。

## 決めたこと

### 手順（この順番で行う）

1. **時計は要求が届いた時点で動き出す**（analyze の route の先頭）。締め切りと段の締め切りは、すべてここからの時間で数える。
   数値は `src/lib/pipeline/time-budget.ts` の1か所にある。
2. **段は実行の順に7つ**: 文の取り出し（`extraction`、①）→ 検索の問いの作成（`queryGeneration`、②。記事全体の検索語は①と並行して書く）→
   検索（`search`）→ ページの取得（`pageFetch`）→ ファクトチェック照会（`factCheck`）→ 資料の関連の判定（`relevanceJudging`）→
   信頼度の判定（`supportJudging`）。
3. **どの外部の呼び出しも、その段の締め切りまでに終わる**（Anthropic・Tavily・ページの取得・JEV・Google Fact Check）。
   - 締め切りまで3秒を切っていたら、新しく始めない。
   - 走っている呼び出しは、締め切りで止める（段の締め切りで止まる合図を、どの呼び出しにも渡す）。
   - Anthropic の再試行と待ちも同じ締め切りの中で行う。待っている間に締め切りが来たら、送り直さない。
   - 各サービス自身の1回の上限（JEV 15秒、Tavily・ページ・Google 10秒）は変えない。締め切りが先に来れば、そこで止まる。
4. **締め切りで止めた・始めなかった呼び出しは「時間切れ」として段ごとに数える。** サービスの失敗には数えない（「各サービスの状態」には出ない）。
   サービスが返した失敗は、これまでどおり失敗のまま扱う。
5. **段ごとに、終わった分で先へ進む。**
   - ①が間に合わない: 主張が1件も無いので、主張0件のまま結果を返す。どの文も確かめていないと画面で知らせる。
   - ②が間に合わない: 問いを書けなかったときと同じ。主張ごとの問いが無ければ、記事全体の検索語で集めた資料で確かめる。
   - 検索が間に合わない: その問いは検索しない（何も見つからなかったのと同じ。検索の失敗にはしない）。
   - 取得が間に合わない: 取得できなかったページと同じ（検索の抜粋を本文にする。今の取得の失敗と同じ扱い）。
   - 照会が間に合わない: 照会の結果なしで進む。見つかった件の照合が間に合わなければ、残りの件は照合しない。
   - 関連の判定が間に合わない: 判定できなかった節を、主張ごとに `evidenceTrace.unjudged`（理由「時間切れ」・節の数・ページの URL を
     判定する予定だった順に）とログに残す。判定できた節のうち線（0.45）以上のものだけで信頼度を問う（ADR-0014 のまま）。
     判定できなかった節を持つページは「関係なし」（`saidNothing`）に数えない。
     **1節も判定できなかった主張は、信頼度を問わない。** 時間のせいで空にした `sources` で問うと、資料ではなく時計についての問いになり、
     低い数値が「資料が無い」ように見えるため。
   - 信頼度の判定が間に合わない: その主張は数値を出さない。理由は「時間内に信頼度の判定が終わらなかったため、確認できませんでした（時間切れ）。」
     （関連を1節も判定できなかった主張は「時間内に資料を判定できなかったため、確認できませんでした（時間切れ）。」）。
     1主張の問いが複数のリクエストに分かれ、一部だけ答えが返ったときも数値を出さない。答えの最大を取る決まり（ADR-0014）では、
     返らなかった答えの方が高いことがあるため。
6. **結果は必ず返す。** `result.cutShort` に、締め切りにかかった段と、始めなかった数・止めた数・締め切りを出す。ログにも段ごとに1行、
   主張ごとに1行（関連を判定できなかった節、数値を出せなかった理由）を出す。
7. **`result.timings` に段ごとの時間を出す**（観測のためだけで、何も決めない）。7つの段それぞれに、時間（ms。段は重なるので、呼び出しが
   1つ以上走っていた時間）、最初に始まった時刻と最後に終わった時刻（開始から）、締め切り、呼び出し数、JEV の呼び出し数（`jevCalls`）、
   始めなかった数・止めた数。今までの `FactVerification`（全体）も残す。

### 時間の設定（数値と根拠）

時刻はすべて要求の開始から。記事05の段ごとの時間は記録が無かったので、全体（184〜195秒）と生成の出力量から割り振った推定である（未測定）。
取り出しは出力 約5,500トークン（29主張）で推定90〜110秒、問いの作成は 約3,000トークンで推定40〜60秒、検索と取得は約10〜15秒、JEV は約20〜30秒。

| 設定 | 値 | 根拠 |
| --- | --- | --- |
| 上限（`PLATFORM_LIMIT_MS`） | 300秒 | Vercel の `maxDuration`（vercel.json、analyze の route）。超えると何も返らない |
| 締め切り（`RUN_DEADLINE_MS`） | 270秒 | 外部の呼び出しはすべてここまでに終える。残り30秒は時計に見えない分: 時計が動く前の関数の起動、締め切りの後の結果の組み立て・JSON化（result と job の2回）・送信、数十の主張が一斉に終わるときのイベントループの遅れ。どれも未測定で、超えると何も返らないので、早めに返る側に倒す |
| 最小の持ち時間（`MIN_START_MS`） | 3秒 | 段の締め切りまでこれを切ったら、その段の呼び出しを始めない。検索・ページ・JEV の1回はふだん1〜3秒で、それより短い残りで始めても答えが届く前に止まる |
| ①文の取り出し | 170秒 | 生成1回。止めると主張が1件も無くなるので、いちばん長く待つ。後ろに100秒（問いの作成40秒＋下の60秒）を残す。記事05は推定90〜110秒で、60秒以上の余裕 |
| ②検索の問いの作成 | 210秒 | ①の後に生成1回。止めても、問いを書けなかったときと同じく記事全体の検索語で確かめられる。記事05は推定140〜160秒で終わり、50秒以上の余裕。後ろに60秒（検索10・取得10・照会5・関連10・信頼度25）を残す |
| 検索（Tavily） | 220秒 | ②の後10秒。Tavily 1回の上限（10秒）と同じ。ふだん1〜3秒 |
| ページの取得 | 230秒 | 検索の後10秒。1ページの上限（10秒）と同じ。本番では毎回3〜8件がこの10秒で切れている |
| ファクトチェック照会 | 235秒 | 取得の後5秒。Google の照会（ふだん1秒前後、上限10秒）と、見つかった件の JEV との照合 |
| 資料の関連の判定（JEV） | 245秒 | 照会の後10秒以上（照会が1秒で終われば約15秒）。記事05の規模では最大 約116回（29主張×4回）・約350万見積もりトークンで、JEV の 250,000トークン/秒なら約14秒 |
| 信頼度の判定（JEV） | 270秒（＝締め切り） | 関連の締め切りの後25秒。ふつう1主張1回で、29回・約90万見積もりトークン＝約4秒。JEV 1回の上限（15秒）を丸ごと1回待てる |

段の締め切りは実行の順に並び、どの段も次の段に最小の持ち時間（3秒）以上を残す。各段が締め切りより前に終われば、この表は何もしない。

### ガイドライン（こうする）

- 時間は時計で守る。数値は `time-budget.ts` の1か所で変える。段の順に並べ、前の段が後ろの段の最低限の時間を残す。
- 止めた場所で「時間切れ」と書いて残す（主張ごとの `unjudged`、主張の理由、`cutShort`、ログ）。黙って捨てない。
- 時間切れはサービスの失敗と分けて数える（ADR-0006 の層を混ぜない。時間切れは層0の時間の上限であり、各サービスの失敗ではない）。
- 終わった分で先へ進み、結果は必ず返す。途中までの結果は、途中までだと画面で言う。
- 締め切りの数値は `result.timings` の実測で直す。直すときは、時間内に終わっている実行が締め切りにかからないことを段ごとの時間で確かめる。

### 禁止事項（これはしない）

- 見積もり（「〜秒で終わるはず」）で打ち切りを決め、時計を見ない。
- 締め切りを過ぎてから新しい呼び出しを始める。締め切りを越えて待つ・送り直す。
- 時間切れで数値を作る（時間のせいで空にした `sources` で問う、答えの一部から最大を取る、を含む）。
- 主張を黙って落とす。判定しなかった資料を黙って捨てる、「関係なし」（`saidNothing`）に数える。
- 時間切れをサービスの失敗として数える。
- 時間に間に合わせるために、資料の選び方（#80 の1主張12万トークンの上限と検索の順）、JEV への問い、表示、80%の線、①（ADR-0020）、
  ②（ADR-0019）を変える。この決定は時間だけを扱う。

### 触らないもの

- ③資料の選び方（ADR-0016 の12万トークンの上限と検索の順）、JEV への問いの文面と渡し方（ADR-0011・0014）、信頼度の表示と80%の線（ADR-0011）、
  ①（ADR-0020）、②（ADR-0019）。
- JEV の送り直しと、同時に送る数の上限は入れない（別の変更）。各サービスの1回の上限も変えない。

### 画面（最小限）

- 数値の無い文: これまでどおり▶が付き、「信頼度 数値なし」、吹き出しに理由「…確認できませんでした（時間切れ）。」（今の「確認できませんでした」の形）。
- 途中までの結果: 本文の上に「時間の上限に近づいたため、途中までの結果をお見せしています。時間内に確かめきれなかった文は「数値なし」に
  なっています。」、詳しい情報に段ごとの数。このときは「気になる箇所は見つかりませんでした」を出さない。
- ①が間に合わなかった: 「時間内に文の取り出しが終わらなかったため、どの文もまだ確かめていません。記事が長いときは、いくつかに分けてから、
  もう一度お試しください。」
- 判定できなかった資料を除いて数値を出した文: 吹き出しに「時間内に読みきれなかった資料があります。数値は、読めた資料だけで出したものです。」
  （ウェブ検索ができなかった文に出す一文と同じ形）。

## 変わらないこと（テストで固定）

- 各段が締め切りより前に終わる実行では、結果も JEV への問いも変わらない（締め切りがある場合と無い場合で、同じ結果・同じ問い）。
  記事05と同じ規模・時間（29主張・約183秒）の偽の実行でも、何も切られず全主張に数値が付く。
- 外部の呼び出しの数と費用は変わらない（時間切れのときは減る）。

## Consequences

- 狙い: 何も返らない（#84 の型）が無くなる。遅い回・長い記事でも、270秒までに途中までの結果が返る。時間内に終わる実行は何も変わらない。
  段ごとの時間で、どの段に時間がかかっているかが本番で見える。
- 恐れ:
  - 締め切りの数値は推定で決めた（段ごとの実測が無い）。本番の記事05の段の時間が推定より遅ければ、時間内に返っていた実行でも問いの作成や
    判定が締め切りにかかり、「数値なし」や読みきれなかった資料が出る。値が回ごとに揺れるもとになる。
  - ①が170秒で終わらない長い記事（未測定。3,000字前後から）は、主張0件で返る。今は300秒を超えて何も返らないはずの記事である。
  - ②が締め切りにかかると、主張ごとの問いの資料が無くなり、信頼度が下がりうる（問いを書けなかったときと同じ）。
  - 時計に見えない分（起動・送信・イベントループの遅れ）が30秒を超えると、まだ300秒を超えうる。未測定。
- 測り方: 本番で記事05を流し、`result.timings` の段ごとの時間と締め切りまでの余裕を見る。`cutShort` が無く、値が前回（184秒・195秒）と
  同じ範囲かを見る。長い記事を1本流し、何秒で返り、どの段が切られたかを見る（費用の決まりに従い1本ずつ）。
- 戻し方: マージ後 `git revert -m 1 <マージのコミット>`。
