# 不具合は層で切り分ける

## Context

一日のうちに、「核心機能が何も検知しない」という同じ症状が、まったく別の原因から次々に出た。

- 配備されていたのは古いコードだった（環境）
- 鍵は登録済みだったが、その配備には反映されていなかった（環境）
- 1回の実行が60秒の上限で打ち切られた（環境）
- 生成の要求に、モデルが受け付けない引数を入れていた（LLMとの連携）
- JEVへの送信形式が仕様と違い、102件すべて拒否された（JEVとの連携）
- 生成の応答が長さ上限で途中終了し、「JSONが壊れている」と表示された（システム）
- 主張と無関係な会社のページを根拠に採用した（システム）

症状はどれも「検知が出ない」で同じだった。層を決めずに直すと、症状ごとの場当たりな修正が積み上がり、
原因の特定そのものが遅れる。実際に遅れた。

## Decision

不具合は次の5層で切り分ける。**必ず上から順に確認する。** 下の層を疑う前に、上の層が白であることを示す。

### 0. 環境・配備

鍵、URL、配備されているコード、実行時間の上限、契約プラン。

- 見分け方: 本番URLが配信しているコードに、直したはずの目印があるか。結果画面の「各サービスの状態」。
  打ち切りなら `FUNCTION_INVOCATION_TIMEOUT`。
- この層が黒なら、コードをいくら読んでも原因は出てこない。

### 1. LLM（生成）

主張の抽出、検索クエリの作成、文章の書き換え。

- 見分け方: 生成された主張文そのものを見る。主語が落ちていないか、原文にない事実が混ざっていないか。
- 例: 「オンライン会員は入会金1万円」が「フリノバのオンライン会員の入会金は1万円である」と
  正規化され、主語も固有名詞も残っていれば、この層は白。

### 2. システム（この製品のコード）

検索クエリの組み立て、候補ページの関連性の門、証拠と主張の突き合わせ、差分検査、画面表示。

- 見分け方: 入口（主張文）と出口（採用された証拠・判定）を並べ、間で何が起きたかを追う。
- 例: 主張が「フリノバ」なのに英会話「NOVA」の料金ページが証拠に入っていれば、
  通してはいけないものを通した門の問題であり、この層。

### 3. 外部の情報源（検索と取得）

検索（どのページを候補に出すか）と取得（本文を読めたか）は**別の層として扱う**。
片方が動いても、もう片方が死んでいることがある。

- 見分け方: 「各サービスの状態」でウェブ検索とページの取得を個別に見る。証拠のURLと抜粋を読む。
- そもそも世の中に情報が無い主張は、この層の限界であって不具合ではない。「要確認」が正しい答え。

### 4. JEV（判定）

渡された主張と証拠に対する、狭い判定。

- 見分け方: **JEVに渡した問いを先に見る。** 主張文と証拠が正しければ、返ってきた判定はJEVの責任。
  問いが誤っていれば、それは1か2の責任であり、JEVは正しく答えている。
- 判定が一律（全部同じ答え、全部未検出）なら、JEVではなく連携（送信形式・鍵）を疑う。

## Consequences

- 報告には必ず「どの層か」を書く。層を書かない報告は、原因を特定していない報告と同じ。
- 「JEVがおかしい」という指摘は、JEVに渡した問いを示してからでないと成立しない。
- 代用（フォールバック）を置かない方針は、この切り分けの前提である。代用は層の境界を消し、
  0〜4のどこで死んだのかを分からなくする。失敗は失敗のまま、どの層で起きたかが見えるようにする。
- 結果画面の「各サービスの状態」は、層0と層3を一目で切り分けるための装置であり、消してはならない。
